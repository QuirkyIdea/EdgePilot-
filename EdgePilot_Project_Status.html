UROP Project · Status & Technical Brief

EdgePilot — Adaptive Telemetry-Budgeted Intelligent Task Offloading

A reproducible simulation study of when to observe and where to compute in dynamic edge–cloud systems, driven by the value of information under an explicit monitoring budget.
Student: Saunaak Mukherji (AP23110010447)  ·  Programme: B.Tech CSE, SRM University–AP  ·  Status date: 2 November 2026

1. What this project is about

In one sentence: EdgePilot studies whether an edge scheduler can be smarter by treating monitoring itself as a costly, budgeted decision made jointly with the decision of where to run each task — instead of monitoring everything blindly or guessing from stale data.

The real-world problem

Edge computing places small servers close to users so that latency-sensitive apps (AR, industrial control, live analytics) don't have to reach a distant cloud. Every task a device creates raises the same question: run it locally, on a nearby edge server, or in the cloud? The best answer changes second-by-second because it depends on live conditions — how busy each edge server is, how much bandwidth a link has right now, whether a path is congested.

There are two naive ways to deal with this, and both are bad:

  • Decide on stale information → the scheduler offloads to a server that just got congested, or keeps a task local when an edge had room. Avoidable mistakes.
  • Monitor everything, all the time → accurate, but every telemetry message costs bandwidth, energy and CPU. At scale the monitoring plane starts competing with the data plane it's meant to help.

The core tension is therefore decision quality vs. monitoring overhead. EdgePilot asks: can the scheduler decide, moment by moment, when observing is actually worth it?

The idea & the proposed algorithm — ABVI-Edge

ABVI-Edge = Adaptive Budgeted Value-of-Information Edge scheduler. For every task it does two coupled things:

  • Where to place the task (local / edge / cloud), and
  • Whether it is worth spending a unit of a finite, shared telemetry budget to refresh its view of a candidate before committing.

A probe is bought only when its Value of Information (the expected reduction in decision cost from seeing the true state) — scaled by task urgency — exceeds an adaptive shadow price that paces the budget over time. This is deliberately smarter than a fixed rule like "refresh if staleness > X", because it also asks would refreshing actually change my decision? A location that is stale but irrelevant, or relevant but already fresh, has near-zero value and is skipped. It uses no machine learning / no training — it's a transparent, white-box controller where every probe is justified by a logged number.

2. Is the research topic unique?

Yes — but the claim is stated narrowly and honestly. A systematic survey of 20+ papers (2018–2026) shows five mature but separate research areas. None of them closes the loop the way EdgePilot does.

Existing research areaWhat it already solvesWhat it does not do
Computation offloading / placement (Wang 2020; firm-deadline MDP 2022; surveys 2023) Optimise latency/energy/deadlinesAssumes the needed state is already available — ignores the cost of getting it
Partial-observation offloading (Badnava 2023; POMDP migration 2022; imperfect-CSI 2024) Act well under incomplete stateNever pays to acquire more information
Age of Information (AoI) (2021–2022) Keep a monitor fresh via transmission schedulingNot coupled to any task-placement decision
Value of Information (VoI) / observation scheduling (2018, 2021, 2024) Buy observations under a budget to improve a decisionTargets generic estimation/control — not offloading
Adaptive network telemetry (PINT 2020, LINT 2021, FineMon 2024, AdapINT 2024) Cut monitoring overhead on the monitoring planeDecoupled from the downstream placement decision

The gap EdgePilot fills: a budget-constrained, VoI-driven policy that jointly decides (a) which servers/links to probe with scarce telemetry and (b) where to place each task, in a dynamic, deadline-driven edge–cloud environment. The ingredients are known; their joint, decision-coupled, budgeted integration for offloading is the under-explored contribution.

Candid caveat (kept in the report): VoI, AoI, budgeted sensing and partial-observation offloading are not individually new. If any paper is found combining all three pillars (offloading + telemetry budget + VoI acquisition), the contribution narrows to our specific shadow-price pacing + urgency-weighted myopic-VoI formulation and its empirical frontier — which is still concrete and reproducible.

4. What is genuinely new in this work

  • New Decision-coupled VoI for offloading. VoI is computed specifically as the expected reduction in the task-placement decision cost — with an inner "would this flip the decision?" test — not as generic estimation error.
  • New Adaptive budget shadow price. A self-pacing price λ(t) that rises when budget is spent too fast and falls when under-spending, automatically reserving budget for future, more valuable decisions.
  • New Urgency-weighted acquisition. Tight deadlines / high priority raise willingness to pay for information, linking monitoring effort to task stakes.
  • New Regret-as-a-lens evaluation. Using oracle-relative scheduling regret to isolate the cost of stale information and show the mechanism directly — a clean empirical characterisation of the quality/overhead frontier.
  • New White-box, reproducible. No RL, no training; every decision is auditable and every result re-runnable from seeds.

5. What is left to do

To do · research depth
  • Sequential (POMDP/RL) VoI to replace the current myopic, single-step estimate — value a probe by its effect on future decisions too.
  • Closed-loop load model so the scheduler's own placements feed back into queue growth (currently load is exogenous / open-loop).
  • Correlated / batched probes — exploit correlation between neighbouring locations instead of pricing each probe independently.
To do · realism & validation
  • Real telemetry traces instead of synthetic OU dynamics.
  • Hardware-in-the-loop check of the estimated energy model.
  • Integrated-interval execution (not just state at task arrival).
  • Fairness across devices in the cost function.
Note: none of these are needed for the central hypothesis, which is already supported. They increase realism/generality and are listed as Future Work in the report.
